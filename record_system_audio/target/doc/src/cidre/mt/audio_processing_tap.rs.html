74/// A function called when an audio track has data to be processed by its tap.
75///
76/// A processing callback is invoked when the audio track has data that can be processed by a
77/// given tap.
78///
79/// The processing callback will be called when there is sufficient input data to provide for
80/// processing. The callback should then go and request as much source data as it needs in order
81/// to produce the requested number of processed samples. When the callback requests source data,
82/// it may receive less data than it requests.
83///
84/// The tap must provide the same number of samples that are being requested. Under normal circumstances,
85/// the source data it requests should be satisfied (as the client running the audio queue is also
86/// providing the queue with the audio source material). If there is insufficient source data available
87/// (this is indicated by the numberFramesOut from the GetSourceAudio call), then the processing tap
88/// should cope as best as it can; it can either return less data than was requested, insert silence,
89/// insert noise, etc.
90/// If less data is returned than requested, the remainder will be filled with silence.
91///
92/// A processing tap is a real-time operation, so the general Core Audio limitations for real-time
93/// processing apply.  For example, care should be taken not to allocate memory or call into
94/// blocking system calls, as this will interfere with the real-time nature of audio playback.
95///
96/// Under normal operation, the source data will be continuous from the last time the callback was
97/// called, and the processed samples should be continuous from the previous samples returned. If
98/// there is any discontinuity between the last samples provided for processing, the audio queue will
99/// set the kMTAudioProcessingTapFlag_StartOfStream bit in the flags. After a discontinuity, the
100/// first sample that the processing tap outputs should correspond to the first sample that was
101/// provided in the source samples (so a reset + consequent process serves to re-anchor a
102/// relationship between the processing tap's source and processed samples). In this case, the
103/// processing tap will typically discard any previous state (for example, if a processing tap was
104/// adding a reverb to a signal, then the discontinuity flag would act the same as AudioUnitReset;
105/// any previous source information in the processing tap should be discarded).
106///
107/// The caller is responsible for absorbing any processing delays. For example, if the
108/// processing is to be done by an audio unit that reports a processing latency, then the caller
109/// should remove those latency samples from the audio unit's rendering and not return them to
110/// the tap.
111///
112/// The processing tap may operate on the provided source data in place ("in-place processing")
113/// and return pointers to that buffer, rather than its own. This is similar to audio
114/// unit render operations. The processing tap will be provided with a bufferList on input
115/// where the mData pointers are NULL.
116///
117/// When the output audio is stopped asynchronously, the processing tap will see the
118/// kMTAudioProcessingTapFlag_EndOfStream bit set on return from GetSourceAudio, and is responsible
119/// for propagating this bit from the callback when its processing has reached this point.
120///
121/// A processing tap will NEVER see the same source data again, so, it should keep its own copy,
122/// if it needs to keep it for further reference past the duration of this call. It also cannot
123/// assume that the pointers to the source data that it retrieves will remain valid AFTER the
124/// processing tap has executed.
125///
126/// Should the processing tap provide custom buffers in bufferListInOut, it should ensure that the
127/// data pointers remain valid until the tap is executed again.
128#[doc(alias = "MTAudioProcessingTapProcessCallback")]
129pub type ProcessCb<const N: usize = 1> = extern "C-unwind" fn(
130    tap: &mut mt::AudioProcessingTap,
131    frames_n: cm::ItemCount,

133    buf_list_in_out: &mut cat::AudioBufList<N>,
134    frames_n_out: &mut cm::ItemCount,
135    flags_out: &mut Flags,
136);

148#[doc(alias = "MTAudioProcessingTapCallbacks")]
149#[derive(Debug)]
150#[repr(C, packed(4))]
151pub struct Cbs<T, const N: usize = 1> {
152    pub version: CbsVersion,
153    pub client_info: *mut T,
154    pub init: Option<InitCb<T>>,
155    pub finalize: Option<FinalizeCb>,
156    pub prepare: Option<PrepareCb>,
157    pub unprepare: Option<UnprepareCb>,
158    pub process: ProcessCb,
159}
160
161impl<T, const N: usize> Default for Cbs<T, N> {
162    fn default() -> Self {
163        Self {
164            version: CbsVersion::V0,
165            client_info: std::ptr::null_mut(),
166            init: Default::default(),
167            finalize: Default::default(),
168            prepare: Default::default(),
169            unprepare: Default::default(),
170            process: default_process,
171        }
172    }
